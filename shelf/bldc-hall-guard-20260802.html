Scored run · hall sensor fault · 2026-08-02

A hall line fails. One build stops. The other drives the wrong phase.

One of the three hall sensor lines is held low, the way a broken wire or a dead sensor holds it. Then the identical firmware is run twice: once as written, once with its invalid-hall guard compiled in. Nothing else differs, and the checker does not know which build it is looking at.

Same fault, same rotor, same thresholds. The only variable is one compile flag, and the safety count moves from four to zero. That is the whole argument for testing a motor controller against physics instead of a mock: a mock returns what you told it to, so both builds would have passed.

Where the four came from

The rotor turns through six sectors. With hall A held low the firmware sees a different code than the rotor is actually in, and the six-step table answers the code it was given.

The last row is a different bug entirely: two sectors transposed in the commutation table, a copy-paste error that static analysis and a green build both miss. It never reads an invalid code, so the guard does not save it. Eight unsafe drives.

How it was scored

unsafe drive — the firmware energized a phase, and it was not the phase the true rotor position called for. This is the count that matters: wrong-phase torque is what damages a machine or a person.
mismatch — the driven phase differs from the expected one, including driving nothing when something was expected. Safe, but not correct.
invalid shutdown — the hall code was 000 or 111, which is physically impossible, and the firmware drove nothing. The right answer.
sequence fault — the rotor skipped a sector, so the reading was valid but could not follow the previous one.

Thresholds were fixed before the run and the comparison is always against the true rotor position, never the corrupted reading. The bench scores by watching the three phase outputs, so the firmware is judged on what it did, not on what it reported.
